# Trunk, pull request и релизы

## Изменения кода

Единственная интеграционная ветка — `trunk`. Любое изменение, включая документацию,
CI, версии и срочные исправления: короткоживущая ветка от актуального `trunk` → PR →
успешный `Checks` → squash merge. Прямые коммиты и push в `trunk` запрещены правилами
проекта и для людей, и для агентов. Нельзя обходить CI или нерешённые замечания.
После слияния рабочую ветку удаляют, когда она больше не нужна.

Не вводим постоянную `develop`, заморозку `trunk` на время приёмки или обязательную
ветку на каждый выпуск. Старайтесь делать небольшие PR и быстро возвращать изменения
в `trunk`; незавершённые функции не должны ломать уже работающие сценарии.

## Отвод кандидата и выпуск

`Prepare release` запускается вручную из `trunk`. После preflight и **до сборки**
отдельное задание создаёт лёгкий Git-тег `rc/<GITHUB_RUN_ID>` на `GITHUB_SHA`,
зафиксированный при запуске. Если `trunk` успел продвинуться, тег и сборка остаются
на исходном SHA. Если коммит уже не является предком `trunk`, подготовка прекращается.
Существующий тег допускается только на том же SHA; переназначения и удаления нет.

Тег — снимок исходников, не доказательство успешной сборки. Даже при последующей
ошибке сборки или отказе на телефоне он сохраняется для аудита. Готовность к приёмке
по-прежнему означает успешный `Prepare release`, а не наличие `rc/…`.

После проверки на телефоне `Review release` создаёт `v<versionName>` на SHA
проверенного кандидата и публикует **те же байты APK**, без пересборки. Смена версии —
тоже PR. Исправления — новый PR, новый запуск подготовки и новый `rc/…`; существующие
`rc/…` и `v…` нельзя перемещать, удалять или использовать для другой сборки.
Кандидаты, подготовленные до внедрения `rc/…`, сохраняют старый маршрут приёмки:
их происхождение проверяется по workflow, SHA и хешу артефакта; задним числом теги
им не создаются. Ранее опубликованные теги и релизы не меняются.

Отдельная релизная ветка понадобится только при реальной поддержке старой линии
параллельно новой. Тогда её можно создать от сохранённого `v…`, перенести нужное
исправление из `trunk` и отдельно настроить CI и разрешённый маршрут выпуска.
Нынешний pipeline намеренно разрешает выпуск только из `trunk`.

## Серверная защита: состояние и конфигурация

**На 2026-09-08 защита не включена.** При проверке GitHub API вернул для rulesets
`403: Upgrade to GitHub Pro or make this repository public to enable this feature`.
Подключённая интеграция также получила `Resource not accessible by integration`
при чтении branch protection. Репозиторий остаётся приватным; тариф и видимость
не менялись. Ни этот документ, ни CI, ни файлы JSON не блокируют прямой push на сервере.
Отслеживание включения и проверки — [issue #3](https://github.com/romarioGI/kanji-hour/issues/3).

Готовые конфигурации для импорта администратором, когда доступна функция:

| Файл | Настройки |
| --- | --- |
| `.github/rulesets/trunk.json` | Только PR; `Checks` от GitHub Actions (app ID 15368); актуальная база; squash/линейная история; закрытые review threads; запрет force-push и удаления; пустой bypass list |
| `.github/rulesets/release-tags.json` | Запрет изменения и удаления `v*` и `rc/*`; пустой bypass list; создание разрешено, чтобы `GITHUB_TOKEN` мог отводить кандидатов и публиковать выпуск |

PR обязателен, но минимальное число внешних approvals сейчас 0. Не подставляем
несуществующего ревьюера и не создаём блокировку самоодобрения при работе через
один GitHub-аккаунт. После подключения второго независимого ревьюера следует поднять
число approvals до 1 и настроить CODEOWNERS для CI, release tooling и signing/.
Это отдельная задача в #3; текущий JSON не обещает обязательного независимого ревью.

**Активация:** для приватного личного репозитория нужен GitHub Pro и аккаунт/токен
с административными правами. В Settings → Rules → Rulesets импортируйте оба JSON,
проверьте режим **Active**, целевые refs, пустой bypass list и сохраните. Импорт файлов
сам по себе в git не активирует правила. Не добавляйте PAT администратора в CI.

После активации проверьте на сервере: прямой push/force-push и удаление `trunk`
отклоняются; PR с красным `Checks` или устаревшей базой не сливается; зелёный актуальный
PR с разрешёнными обсуждениями сливается через squash; новые `rc/…` и `v…` создаются,
а перемещение/удаление существующих тегов отклоняется. Тесты JSON проверяют намерение,
а не заменяют эти серверные проверки. Не проверяйте удаление настоящего релизного тега.

В Settings → General можно дополнительно включить автоматическое удаление слитых
рабочих веток. Само включение настроек не входит в эффект этих двух JSON.
Приёмка APK не становится required check для обычного PR.

## Обоснование

Тег на коммите `trunk` — достаточная точка выпуска для текущей схемы. Постоянная
релизная ветка без отдельной линии сопровождения добавила бы лишние переносы изменений.
Ветвление позднее от сохранённого тега остаётся доступным.

- [Trunk Based Development: release from trunk](https://trunkbaseddevelopment.com/release-from-trunk/).
- [Trunk Based Development: branch for release](https://trunkbaseddevelopment.com/branch-for-release/).
- [GitHub: rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/about-rulesets).
- [GitHub: available rules](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets).
