# Выпуск APK

`CI` проверяет PR и изменения в `trunk`. `Prepare release` собирает и подписывает
APK, проверяет его на эмуляторах. После успешной подготовки автоматически
запускается `Review release`: он ждёт приёмки через **Review deployments**.
Зелёная сборка — готовность к проверке на телефоне, не состоявшийся релиз.

## Настроить окружения один раз

Владелец настраивает **Settings → Environments** до слияния изменения workflow.
Строка `environment:` в YAML сама не включает защиту: отсутствующее окружение
GitHub может создать без ограничений. Эти настройки не заменяют защиту `trunk` из #3.

| Окружение | Назначение | Настройки |
| --- | --- | --- |
| `signing` | Подпись кандидата до приёмки | Два исходных signing secrets; без required reviewers. |
| `release` | Приёмка уже проверенного кандидата | Required reviewers: `romarioGI`; секретов нет. |

В обоих окружениях: **Deployment branches and tags → Selected branches and tags →
Branch: trunk**. Не добавлять другие ветки и теги. Не использовать «Protected branches
only», пока защита веток не проверена: при отсутствии защищённых веток это допускает все.

Для `release` отключить **Allow administrators to bypass configured protection rules**.
**Prevent self-review** пока не включать: владелец должен иметь возможность проверить
кандидата, подготовку которого он сам запустил. Второго reviewer добавлять только после
подтверждения его GitHub-логина и доступа, не подставлять имя Akane-san из описания проекта.
Ручная приёмка выпуска не является обязательной проверкой каждого PR.

## Ключ подписи

В **Environment secrets** окружения `signing` сохранить исходную пару:

| Secret | Значение |
| --- | --- |
| `KANJI_SIGNING_KEY_B64` | Base64 исходного `signing/development.p12` |
| `KANJI_SIGNING_PASSWORD` | Пароль из `signing/development-password.txt` |

Из локальной копии с исходными файлами, через авторизованный GitHub CLI:

```sh
base64 < signing/development.p12 | gh secret set KANJI_SIGNING_KEY_B64 --repo romarioGI/kanji-hour --env signing
gh secret set KANJI_SIGNING_PASSWORD --repo romarioGI/kanji-hour --env signing < signing/development-password.txt
```

После сохранения обоих environment secrets удалить прежние **repository**-копии
в **Settings → Secrets and variables → Actions**. Оставленные там копии доступны
и заданиям без окружения; строка `environment: signing` не изолирует их автоматически.
Затем можно сливать изменение workflow. Без переноса ключа новая подпись не заработает.

Не создавать другую пару: APK должен обновлять установленное приложение.
Сертификат сверяется с отпечатком из [инструкции по подписи](../signing/README.md).
Без ключа или с другой подписью подготовка останавливается. Исходные файлы и резервную
копию хранить отдельно от GitHub; secrets не заменяют резервную копию. Не помещать ключ
и пароль в коммиты, логи, артефакты или окружение `release`. Base64 не является шифрованием.

## Подготовить кандидата

1. Внести изменения через ветку и PR в `trunk`, дождаться успешного `Checks`.
   Перед следующей опубликованной версией изменить `versionName` в
   `app/src/main/AndroidManifest.xml` через такой же PR.
2. Открыть **Actions → Prepare release → Run workflow**, выбрать `trunk`.
3. После успешного завершения скачать из **Summary** `release-candidate-<номер запуска>`,
   распаковать `kanji-hour.apk`. Сохранить номер кандидата и его SHA-256.

После перехода на новую схему нужен **новый** запуск `Prepare release`.
Старые кандидаты, подготовленные до перехода, автоматически на приёмку не отправляются;
прежняя ручная форма `Review release → Run workflow` отключена. При переходе проверить
старые запуски ручного Review release: повторный запуск старого workflow исполняет старый
код, а не новый. Не повторять его для публикации; доступные повторному запуску старые
маршруты должны быть устранены до объявления миграции завершённой.

Кандидат хранится 14 дней. Тесты, сборка и подпись используют один SHA коммита,
зафиксированный при запуске. Новые изменения в `trunk` его не меняют.
После приёмки `Review release` создаёт `v<versionName>` на этом коммите.
Релизные ветки и `rc`-теги не нужны. Не переносить и не удалять релизные теги.

`versionCode = 2 + номер запуска Prepare release`. Каждый новый запуск получает
новый код, включая кандидаты после отказа. Не сбрасывать счётчик и не переносить
подготовку в новый workflow без миграции нумерации. Для подготовки **Re-run jobs
запрещён**: нужен новый **Run workflow**. Для локальной установки поверх CI-сборки
передавать подходящий `--version-code`; манифест не меняется автоматически.

## Проверить и принять

На целевом телефоне проверить установку поверх предыдущей версии и сохранение
настроек, запуск, виджет и текущий статичный фон блокировки, смену часа с закрытым
приложением и восстановление обновлений после перезагрузки. Зафиксировать фактическую
модель, версию Android/HyperOS и результаты; не отмечать невыполненные проверки как успешные.

Открыть **Actions → Review release → Review APK candidate <номер сборки> →
Review deployments**, выбрать `release`. Ссылка окружения ведёт на исходную сборку.
Для **Approve and deploy** добавить комментарий такого вида, заменив обе строки:

```text
SHA-256: <64 символа SHA-256 фактически проверенного APK>
<Телефон, версия Android/HyperOS и фактический результат проверки>
```

Для **Reject** достаточно причины отказа, SHA-256 не обязателен.
Подпись и автоматические проверки уже закончены до этого шага; скачивание APK
не требует предварительного одобрения его приёмки.

**Approve:** код читает настоящее решение GitHub для этого запуска и окружения
`release`, сохраняет автора решения (не инициатора сборки) и отчёт. Проверяются источник
кандидата, контрольные суммы и совпадение с SHA-256 из комментария. Публикуются исходные
байты APK, его `.sha256` и `build-info.json`: без пересборки, переподписи и изменения версии.
Сначала заполняется черновик, затем проверяются загруженные файлы и открывается релиз.
Успешный этап `acceptance` означает прохождение согласования, не публикацию:
результат выпуска определяется заданием `publish` и появлением GitHub Release.

**Reject:** публикации нет, выпуск завершается отрицательно. Отдельное задание без
права публикации записывает отказ в статус кандидата. История решений дополнительно
проверяется при повторном запуске: прошлый Reject нельзя превратить в Approve, даже
если запись статуса временно не сработала. После исправлений нужен новый кандидат.
Уже опубликованный выпуск кнопкой Reject не отменяется.

**Нет решения:** при настроенном окружении workflow ждёт; релиза нет. Если reviewers
не настроены или история подтверждений недоступна, публикация останавливается с ошибкой,
а не считает зелёную сборку приёмкой. Отмена workflow или технический сбой не выдаются за Reject.

После технического сбоя публикации можно повторить **Review release → Re-run failed jobs**
для того же запуска: кандидат не меняется, файлы сверяются, а не перезаписываются.
Повторные Approve должны указывать один и тот же SHA-256. При неверном комментарии,
истёкшем артефакте или исправлении самого кода workflow готовить нового кандидата:
повторный запуск использует исходный коммит, а не обновлённый `trunk`.

## Задачи приёмки и автоматические проверки

`Release review issues` после подготовки создаёт issue с APK, чек-листом и фактическим
сроком хранения. Новый готовый кандидат закрывает старую задачу; ошибка сборки её не
заменяет. Публикация закрывает задачу как выполненную, явный отказ — как отменённую.
Закрытие issue само по себе не является приёмкой. Чек-листы при повторной сверке сохраняются.
Обработка идёт по событиям `Prepare release` / `Review release` и публикации, без cron.
После сбоя можно вручную повторить `Release review issues`; истечение срока артефакта
само по себе workflow не запускает.

`CI`: XML, словарь, JVM-тесты, тесты выпуска и сборка без подписи.
`Prepare release` повторяет их, подписывает исходным ключом и проверяет пакет, версию,
SDK, разрешения, данные, подпись и zipalign. Один и тот же APK устанавливается и запускается
на эмуляторах API 34 и 35. После первого опубликованного выпуска проверяется также
установка поверх предыдущего APK без удаления приложения. Настройки пользователя и
поведение HyperOS остаются частью ручной проверки; smoke не является e2e часового обновления.

Ожидание приёмки не занимает runner и не блокирует другие кандидаты. Последовательно
выполняется только публикация после подтверждения. Используются стандартные Ubuntu runners,
без постоянного сервера. Сроки хранения: промежуточная сборка — 1 день, логи эмулятора —
3 дня, кандидат — 14 дней, отчёт приёмки — 30 дней. Тариф и лимиты расходов workflow не меняет.
SDK: Platform 35 r2, Build Tools 35.0.1; JDK 17, Python 3.13. Точные версии записываются
в `build-info.json`; побитовая повторимость на разных версиях инструментов не заявляется.

## Проверка перехода и границы

Перед закрытием #2 владелец проверяет настройки окружений и на пробных кандидатах:
ожидание без решения, Reject без релиза и Approve с публикацией ровно проверенного APK.
Автоматические тесты с подменённым API не заменяют эти реальные проверки и приёмку телефона.
Агент не нажимает Approve от имени человека и не публикует пробный APK без его проверки.

Код `workflow_run` берётся из доверенного `trunk`, не из PR или архива кандидата.
Однако правила внутри Python и YAML не защищают от изменения самих workflow участником
с правом записи: серверная защита ветки, тегов и ключей остаётся в #3.

Документация GitHub: [окружения](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/manage-environments),
[Review deployments](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/review-deployments),
[история решений API](https://docs.github.com/en/rest/actions/workflow-runs#get-the-review-history-for-a-workflow-run).
