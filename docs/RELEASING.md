# Выпуск APK

`CI` проверяет pull request и изменения в `trunk`. `Prepare release` готовит APK.
`Review release` принимает результат проверки на телефоне и публикует выпуск.
Зелёный `Prepare release` — готовность к приёмке, не состоявшийся релиз.

## Ключ подписи

До первого кандидата добавьте в **Settings → Secrets and variables → Actions**
два repository secret:

| Secret | Значение |
| --- | --- |
| `KANJI_SIGNING_KEY_B64` | Base64 исходного `signing/development.p12` |
| `KANJI_SIGNING_PASSWORD` | Пароль из `signing/development-password.txt` |

Через уже авторизованный GitHub CLI, из локальной копии с исходными файлами:

```sh
base64 < signing/development.p12 | gh secret set KANJI_SIGNING_KEY_B64 --repo romarioGI/kanji-hour
gh secret set KANJI_SIGNING_PASSWORD --repo romarioGI/kanji-hour < signing/development-password.txt
```

Не создавайте другую пару: APK должен обновлять установленное приложение.
Сертификат сверяется с отпечатком из [инструкции по подписи](../signing/README.md).
Без ключа или с другой подписью подготовка завершается ошибкой. Резервная копия
нужна отдельно от GitHub; secrets не заменяют её. В коммиты, логи и артефакты
ключ и пароль не попадают. Base64 — формат передачи, не шифрование.

## Подготовить кандидата

1. Внесите изменения в `trunk`. Перед следующей опубликованной версией измените
   `versionName` в `app/src/main/AndroidManifest.xml`.
2. Откройте **Actions → Prepare release → Run workflow**, выберите `trunk`.
3. После успешного завершения откройте **Summary**. Скачайте
   `release-candidate-<номер запуска>`, распакуйте `kanji-hour.apk`.
   Сохраните номер кандидата и SHA-256 из Summary.

Кандидат хранится 14 дней. Тесты, сборка и подпись используют один SHA коммита,
зафиксированный при запуске. Новые изменения в `trunk` его не меняют.

После успешной подготовки `Release review issues` создаёт issue с APK, чек-листом
и дедлайном из срока хранения артефакта. Новый готовый кандидат закрывает старую
задачу как устаревшую. Ошибка или отмена сборки её не закрывает.
При публикации задача закрывается как выполненная, при отклонении — как отменённая.
Закрытие issue не заменяет решение в `Review release`.

Обработка запускается событиями завершения `Prepare release` / `Review release`
и публикации релиза, без cron и опроса по расписанию. Изменение обработчика в `trunk`
также запускает сверку существующих задач. После технической ошибки можно повторить
`Release review issues` вручную: дубли не создаются, чек-листы сохраняются.
Истечение срока артефакта само по себе не запускает workflow.

`versionCode = 2 + номер запуска Prepare release`. Каждый новый запуск получает
новый код, включая кандидаты после отказа. Не сбрасывайте счётчик и не переносите
подготовку в новый workflow без миграции нумерации. `Re-run jobs` для подготовки
запрещён: нужен новый **Run workflow**. Для локальной установки поверх CI-сборки
передавайте сборщику подходящий `--version-code`; значение из манифеста не меняется автоматически.

## Проверить и принять

На целевом телефоне проверьте установку поверх предыдущей версии и сохранение
настроек, запуск и виджет, применение выбранного статичного фона, смену часа
с закрытым приложением и восстановление обновлений после перезагрузки.
Результат фиксируйте с моделью телефона и версией Android/HyperOS.

Откройте **Actions → Review release → Run workflow**, выберите `trunk`:

| Поле | Что указать |
| --- | --- |
| `candidate_run_id` | Номер запуска из Summary кандидата, не `versionCode` |
| `decision` | `approve` или `reject` |
| `tested_sha256` | SHA-256 проверенного APK; для `reject` можно оставить пустым |
| `phone_report` | Телефон, версия ОС и результат либо причина отказа |

**Approve:** проверяются успешность подготовки, источник и контрольные суммы.
Создаются тег `v<versionName>` на исходный коммит и GitHub Release с этим APK,
его `.sha256` и `build-info.json`. После приёмки нет пересборки и переподписи.
Сначала заполняется черновик, публикация происходит после проверки загруженных файлов.

**Reject:** приёмка завершается ошибкой, кандидат отмечается отклонённым, выпуск
не публикуется. Этот кандидат больше нельзя одобрить; после исправления подготовьте новый.
Опубликованный выпуск нельзя отменить кнопкой Reject.

Если решения нет, релиза нет. Подготовка уже завершена и не занимает runner
в ожидании человека. Решение сохраняется в статусе коммита и артефакте приёмки.
Если публикация прервалась из-за технической ошибки, повторите `Review release`
для того же кандидата: уже загруженные файлы сверяются, а не перезаписываются.
При истёкшем или удалённом артефакте нужна новая подготовка.

## Автоматические проверки

`CI`: XML, словарь, существующие JVM-тесты, тесты процесса выпуска и сборка
без подписи. `Prepare release` повторяет их, подписывает APK исходным ключом,
проверяет пакет, версию, SDK, разрешения, данные, подпись и zipalign.

Затем один и тот же APK устанавливается и запускается на эмуляторах API 34 и 35.
После первого опубликованного выпуска дополнительно проверяется установка
поверх предыдущего APK без удаления приложения. Содержимое пользовательских
настроек и поведение HyperOS остаются частью ручной проверки. Это не e2e-тест
часового обновления виджета или обоев.

Используются стандартные Ubuntu runners, без платного ожидания согласования
и без постоянного сервера. Эмуляторы запускаются только при подготовке выпуска.
Сроки хранения: промежуточная сборка — 1 день, логи эмулятора — 3 дня,
кандидат — 14 дней, отчёт приёмки — 30 дней. GitHub учитывает минуты и хранение
по действующему тарифу; сам workflow тариф и лимит расходов не меняет.

SDK зафиксирован: Platform 35 r2, Build Tools 35.0.1. Используются JDK 17 и Python 3.13;
их точные версии записываются в `build-info.json`. Побитовая повторимость сборки
на разных версиях инструментов не заявляется. Внешние Actions закреплены по SHA.
