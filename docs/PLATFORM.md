# Платформа

Версия исходников 0.3.1-poco. Целевое устройство: POCO X5 Pro 5G, Android 14
(UKQ1.240624.001), HyperOS 2.0.11.0.UMSRUXM, 1080 × 2400.

Главный экран — прозрачный AppWidget/RemoteViews. Блокировка — статичное изображение
через WallpaperManager.setBitmap(FLAG_LOCK), а не интерактивный слой. AOD не поддерживается.

## Только текущий фон

CurrentWallpaperImporter проверяет ID и тип текущих обоев. Отдельная блокировка
читается через getWallpaperFile(FLAG_LOCK). Общий фон читается через FLAG_SYSTEM
только при отрицательном ID блокировки и подтверждённом статичном домашнем фоне.
Положительный отдельный ID не разрешает подменить недоступную блокировку домашней.
ID 0, исключение API, живые обои и отказ чтения запрещают запись.

Новый источник сохраняется в приватный PNG с ограниченным декодированием до 2800
по большей стороне. Собственные обои распознаются по ID и используют чистую копию;
потерянный исходник не восстанавливается чтением картинки с уже вписанным кандзи.
Фотодиалог, синий фон и автоматические подстановки удалены. Старый lock-background.jpg
используется лишь как чистый исходник подтверждённых собственных обоев версии 0.2.

Ручная замена обоев не сбрасывает lock_enabled. При следующем запуске обрабатывается
новый фон, в том числе внутри прежнего часа. Если фон временно недоступен, запись
пропускается, ошибка отображается, следующие проверки продолжаются.
При отключении сначала сохраняется выключенное состояние; чистый фон возвращается
только поверх собственных обоев. Внешний фон не заменяется старой копией.

## Защита записи

Все операции сериализованы. ID проверяется после чтения, после рендера и перед записью.
Чистый источник и журнал намерения записываются синхронно до setBitmap. Если результат
системной записи неизвестен после сбоя процесса, текущий ID помечается сомнительным:
он не импортируется, пока пользователь не установит фон заново. Так нельзя гарантировать
автовосстановление во всех сбоях, но можно избежать повторного вписывания старого знака.
При обнаруженной смене ДО вызова setBitmap журнал снимается и новый фон проверяется
в следующий раз без требования ещё одной ручной смены.

Публичный API не предоставляет атомарной операции «записать, только если ID прежний».
Между последней проверкой и setBitmap остаётся небольшая гонка. Нестандартные темы,
карусели и неверные ответы OEM API требуют отдельной проверки, не считаются совместимыми
по результатам JVM-тестов. Кадрирование и создание отдельной блокировки могут отличаться
от исходного оформления Android; удаление кандзи не восстанавливает живой движок или
связь общего фона двух экранов.

## Разрешения и запуск

SET_WALLPAPER — запись блокировки; RECEIVE_BOOT_COMPLETED — восстановление расписания
после загрузки и первого разблокирования; SCHEDULE_EXACT_ALARM — точное событие.
MANAGE_EXTERNAL_STORAGE требуется для чтения новых обоев обычным приложением на Android 14.
Доступ запрашивается явно, без сканирования каталогов. Для автоматического подхвата новых
фонов его нужно сохранять. Публикация в магазине требует отдельной проверки разрешений.

AlarmManager назначает следующий час до очереди обработки. Независимый persisted
JobScheduler с периодом 30 минут страхует режим только блокировки и отзыв точного доступа.
Уже существующее периодическое задание не переносится каждым обновлением. Оба механизма
отключаются, когда выключена блокировка и нет виджетов. Период не гарантирует предельную
задержку в Doze или HyperOS. Foreground-сервис и постоянное уведомление не используются.

ACTION_WALLPAPER_CHANGED зарегистрирован динамически в Application: это ускорение,
пока процесс существует, а не способ запускать убитое приложение. Проверка актуального
фона всегда выполняется и по alarm, recovery, обновлению виджета и открытию приложения.
